# 行业场景清单（智慧工厂 / 智慧农业 / 智慧水务 / 智慧楼宇 / 车联网 / 储能光伏 / 充电桩）

> 主理人识别到场景关键词时，先按本清单的「必问项」补全信息（一次性问完，不反复追问），再按「方案要点」编排，并主动提示「典型坑」。

## 一、智慧工厂

**必问项**
1. 需要采集的设备类型（PLC 品牌、仪表协议、数控机床、机器人、能耗表）
2. 现有网络（有线工业以太网/无线/是否允许改线）、是否有 PLC 编程权限
3. 上位机现状（有无 SCADA/MES/组态软件，是否允许旁路采集）
4. 采集频率要求（秒级/分钟级）与实时控制需求（只读监控 vs 需反向下发）
5. 停机窗口与验收标准（数据准确率、可用率指标）

**典型坑**
- 直接改 PLC 程序引发产线停机风险 → 优先旁路采集（网关读 Modbus/OPC UA）
- 老设备无通信口 → 加装传感器或电表间接采集
- 车间电磁干扰导致无线丢包 → 有线优先，无线需评估 2.4G/5G 共存
- 数据只上云不落本地 → 断网时数据丢失，需边缘缓存补传

**方案要点**
- 拓扑：设备 → 边缘网关（协议转换 + 本地缓存）→ 平台（MQTT/HTTPS）
- 物模型：按设备类型建模，属性含运行状态/能耗/告警阈值
- 数据质量重点：完整性（断网补传）、时效性（秒级场景延迟）、一致性（多源同一测点）
- 扩展：OEE、能耗分析、预测性维护需额外数据源（工单/排产）

## 二、智慧农业

**必问项**
1. 监测对象（土壤温湿度/PH/EC、气象、大棚环境、灌溉阀门、养殖水质）
2. 覆盖面积与地形（决定 LoRa/NB-IoT 组网与网关数量）
3. 供电条件（市电/太阳能+电池，决定功耗预算与上报频率）
4. 网络覆盖（有无 4G 信号，是否需要 LoRa 自组网）
5. 控制需求（是否需远程开关水泵/卷帘/风机）

**典型坑**
- 忽略供电：电池设备按分钟级上报，几个月就没电 → 上报周期与休眠策略必须一起设计
- 土壤传感器埋深/点位不规范 → 数据失真，需给出布点规范
- 农忙期信号遮挡/设备被盗 → 需离线缓存 + 设备定位/防拆
- 控制类指令无回执 → 阀门实际未动作但平台显示成功，需状态回传校验

**方案要点**
- 拓扑：传感器 → LoRa/NB-IoT → 网关/直连 → 平台；控制走下行指令 + 状态回传
- 功耗设计：休眠 + 定时唤醒 + 变化上报，电池寿命目标 ≥1 年
- 数据质量重点：完整性（信号盲区）、准确性（传感器漂移需定期校准）、一致性（单位统一）
- 扩展：与气象预报/灌溉模型联动需外部数据源

## 三、智慧水务（水表/管网/泵站）

**必问项**
1. 计量对象（户表/大表/管网压力/水质/流量计）与表计协议（DL/T 645、CJ/T 188、M-Bus、Modbus）
2. 抄表方式（现有有线/无线远传/人工抄表）与改造约束
3. 数据用途（计费 vs 漏损分析 vs 压力调度，决定精度与频率要求）
4. 设备数量与分布（小区/城区，决定 NB-IoT 蜂窝方案可行性）
5. 与现有营收系统/SCADA 的对接要求

**典型坑**
- 计费类数据对准确性要求极高，需双向校验与日冻结数据核对
- 表计电池寿命与抄表频率冲突（日冻结 vs 实时上报功耗差异大）
- 管网压力突变常被误判为异常，需结合工况基线判定
- 多厂商表计协议不一 → 需统一接入网关或平台侧协议适配

**方案要点**
- 拓扑：NB-IoT 表计直连 / M-Bus 总线 + 集中器 / Modbus 泵站网关
- 数据质量重点：完整性（日冻结必到）、准确性（表底数连续性与倒走检测）、时效性（计费类可容忍小时级）
- 专项校验：表底数只增不减、用量与温度/季节相关性、总分表差额（产销差）
- 扩展：漏损分析需分区计量（DMA）+ 夜间最小流量法

## 四、智慧楼宇

**必问项**
1. 子系统范围（暖通空调 BA、照明、电梯、门禁、消防、能耗计量）
2. 现有系统与协议（BACnet、Modbus、KNX、厂商私有协议、是否开放接口）
3. 网络与安全要求（是否与办公网隔离、等保要求）
4. 管理目标（节能率指标、舒适度、运维工单联动）
5. 是否需与既有 IBMS/物业平台对接

**典型坑**
- 厂商私有协议不开放 → 需协议网关或厂商配合，前期必须确认接口文档
- 跨系统联动（如消防火警联动电梯归位）涉及安全责任 → 需明确边界与验收
- 机电设备数据点极多（单栋数千点），物模型不规划会导致后期混乱
- 节能改造缺少基线数据 → 先做 3–6 个月计量基线再谈节能率

**方案要点**
- 拓扑：子系统 → 协议网关（BACnet/Modbus 转 MQTT）→ 平台；强弱电隔离
- 物模型：按「楼层-机房-设备-点位」四级编码规划 identifier
- 数据质量重点：一致性（点位命名/单位统一）、完整性（数千点位的上报率监控）、时效性（BA 控制回路秒级）
- 扩展：节能分析需分项计量（照明/空调/动力分开）

## 五、车联网 / 车队管理（T-Box / CAN 总线）

**必问项**
1. 车型与总线（CAN/CAN FD、J1939 商用车 / 乘用车私有协议；是否需网关取 CAN 数据）
2. 采集内容（位置/车速/里程、电池 SOC/SOH、故障码 DTC、驾驶行为、胎压）
3. 通信与功耗（4G/5G 在线时长、驻车休眠策略、流量套餐谁承担）
4. 上报策略（周期上报 vs 事件触发；弱网区域断点续传要求）
5. 合规与数据归属（车辆数据出境/本地化要求、车主授权、平台对接方是谁）

**典型坑**
- 直接读 CAN 原始报文却无 DBC 解密文件 → 数据无法释义，必须先拿到主机厂 DBC/协议文档
- 驻车仍高频上报 → 电瓶亏电，需设计休眠唤醒与触发条件
- 里程/位置依赖单一 GPS → 隧道/地库丢星，需惯导或多源融合兜底
- 把故障码 DTC 当普通遥测处理 → 缺严重度分级与告警抑制，运维被刷屏
- 忽略 OTA 升级对行车安全的影响 → 行驶中禁止升级，需驻车+电量双重校验

**方案要点**
- 拓扑：T-Box → 车载 CAN 网关 → 4G/5G → 平台（MQTT over TLS）；车机侧本地缓存
- 物模型：属性（车辆状态/电池/位置）+ 事件（故障码/碰撞/超速）+ 服务（远程诊断/空调预热），测点必须标注 CAN 报文 ID 与信号位
- 数据质量重点：时效性（弱网延迟与补传）、一致性（多源位置融合）、完整性（驻车休眠期数据缺口要可解释）
- 扩展：驾驶行为评分需高频采样（≥10Hz）与边缘聚合；预测性维护需 DTC 历史 + 零部件台账

## 六、储能 / 光伏电站

**必问项**
1. 系统类型（电化学储能 / 分布式光伏 / 光储一体；grid-tie 并网还是离网）
2. 设备构成（PCS、BMS、电池簇、逆变器、汇流箱、电表、气象站）
3. 通信协议（Modbus RTU/TCP、IEC 61850、IEC 104、厂家私有协议）
4. 采集与安全边界（遥测只读取 vs 需 EMS 下发调度指令；并网调度接口归属）
5. 安全合规（电池热失控预警、消防联动、电力监控二次系统安全防护要求）

**典型坑**
- 直接对 PCS/BMS 下发控制指令 → 涉及电网调度与人身安全，必须由持证 EMS/调度系统执行，平台只做只读监控与建议
- 电池簇数据不同步 → 多 BMS 时钟未对齐，SOC/温度对比失真，需时钟同步（NTP/PTP）
- 只采总表不采分项 → 无法定位发电效率损失，需组串级/电池簇级采集
- 忽略采样频率差异 → 电气量秒级、气象分钟级，不区分口径直接算相关性会得出错误结论
- 热失控预警阈值照搬通用值 → 不同电芯体系（磷酸铁锂/三元）阈值不同，需按厂家规格与实测基线设定

**方案要点**
- 拓扑：设备 → 场站网关（协议转换 + 边缘缓存）→ 平台（MQTT/IEC 104）；控制链路与采集链路物理/逻辑隔离
- 物模型：属性（电压/电流/功率/SOC/温度/发电量）+ 事件（过温/绝缘故障/并离网切换）+ 服务（只读查询；控制类服务必须标注"需人工确认"）
- 数据质量重点：一致性（多表勾稽：总发电量 ≈ 各逆变器之和）、时效性（秒级电气量）、完整性（夜间光伏零发电不能算缺失）
- 扩展：效率分析需辐照度/组件温度数据；收益测算需电价与并网计量口径；安全预警需分级（P0 热失控立即处置）

## 七、充电桩 / 充电场站

**必问项**
1. 场站规模与类型（直流快充 / 交流慢充 / 光储充一体；有多少枪、多少场站）
2. 协议标准（OCPP 1.6J / 2.0.1、国标 27930、厂家私有协议；平台是否已对接运营商）
3. 业务链路（谁做计费与结算、是否需要与电网/运营商分账、用户支付方式）
4. 采集内容（枪状态/充电功率/电量/SOC、故障码、订单与计费流水）
5. 网络与运维（场站网络质量、远程重启与固件升级需求、运维响应 SLA）

**典型坑**
- 把充电过程数据当普通遥测 → 订单/计费流水是业务关键数据，需 QoS 1 + 持久化 + 对账机制，不能丢
- OCPP 版本混淆 → 1.6 与 2.0 报文结构和能力差异大，先确认桩端版本再选平台
- 枪状态不同步 → 平台显示空闲但物理占用，需心跳 + 状态上报双保险，并设超时纠正
- 忽略计费准确性 → 电量计量误差/分时电价切换时点错误会引发用户投诉，需与计量检定口径对齐
- 场站弱网下固件升级 → 断点续传 + 失败回滚 + 非营业时段升级，避免占用用户充电时间

**方案要点**
- 拓扑：充电桩 → 场站网关/直连 → 平台（OCPP over WebSocket / MQTT）；计费流水单独链路持久化
- 物模型：属性（枪状态/输出功率/电量/SOC/温度）+ 事件（故障/急停/充电完成）+ 服务（启动/停止充电、远程重启；计费类操作需二次确认）
- 数据质量重点：完整性（订单流水不丢）、一致性（平台电量 vs 桩端计量 vs 电网表三方对账）、时效性（枪状态秒级同步）
- 扩展：负荷预测与有序充电需电网容量与分时电价数据；运营分析需场站/枪维度聚合；OCPP 与自有物模型之间需明确映射关系

## 通用收尾（七个场景都适用）

1. 明确**验收指标**：设备在线率 ≥98%、数据完整率 ≥95%、端到端延迟 ≤Ns
2. 明确**分期实施**：一期试点 1 个区域/1 类设备，验证后复制
3. 主动指出**数据安全与合规**：设备鉴权、传输加密、数据不出域要求
4. 给出**成本量级**（引用 references/cost-baseline.md）并区分一次性与持续投入
