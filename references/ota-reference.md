# OTA 升级参考（流程 / 灰度 / 断点 / 回滚 / 指标）

> 供 device-access-engineer 与主理人引用。OTA 方案必须回答：怎么灰度、断了怎么办、坏了怎么回、怎么防篡改。

## 一、标准 OTA 流程

```
固件包管理（版本号+签名+元数据）
  → 灰度分组（按型号/地域/批次）
  → 分片下发（支持断点续传）
  → 设备端校验（签名 + 哈希）
  → 安装（双分区切换 或 原地升级）
  → 上报结果（成功/失败原因码）
  → 观察窗口 → 扩大灰度 或 暂停
```

## 二、灰度策略（默认推荐）

| 阶段 | 比例 | 观察窗口 | 进入下一阶段条件 |
|------|------|----------|------------------|
| 内测 | 1%（或固定 5–10 台） | ≥24h | 成功率 ≥98%，无变砖 |
| 小批量 | 5% | ≥24h | 成功率 ≥98% |
| 扩大 | 20% | ≥24h | 失败率 <2% |
| 全量 | 100% | - | - |

- 分组维度：设备型号、地域、客户、出厂批次（任选或组合）
- **自动熔断**：失败率超过 2% 或出现变砖 → 自动暂停并回滚灰度组
- 低功耗设备：升级前校验电量（建议 >30%）与信号强度，否则延后

## 三、断点续传与差分

- 分片大小 4–16 KB，支持 HTTP Range 或平台分片协议
- 断点信息持久化在设备侧（掉电可恢复）
- **差分升级**：新旧版本二进制差分，流量可降 60%–90%，适合 NB-IoT / 流量计费场景
- 并发限速：大批量设备同时下载会打爆出口带宽与运营商网络，需按批次限速（如每分钟 500 台）

## 四、回滚方案（必须在方案中出现）

| 方案 | 说明 | 适用 |
|------|------|------|
| A/B 双分区 | 新固件写入备分区，校验通过后切换；失败切回原分区 | 推荐（存储足够时） |
| 单分区 + 保留旧版 | 保留上一版本镜像，启动失败自动回滚 | 存储受限设备 |
| 无法回滚 | 必须提前说明风险，加大灰度与观察窗口 | 尽量避免 |

- 回滚触发条件：启动失败 N 次、心跳在 M 分钟内未恢复、关键自检项失败
- **防降级**：固件版本号必须单调递增，拒绝安装旧版本（防攻击者刷回有漏洞版本）

## 五、安全要求

- 固件包**签名**（私钥离线保管，推荐 HSM/离线机器），设备端**验签后**才允许安装
- 校验哈希（SHA-256）防传输损坏
- 下载通道使用 HTTPS/TLS，禁止明文 HTTP
- 升级指令需鉴权，防止伪造批量升级指令

## 六、监控指标（方案中应给出）

- 升级成功率、平均升级耗时、失败原因分布（网络 / 电量 / 存储不足 / 校验失败 / 安装失败）
- 变砖率（关键红线，>0.1% 必须暂停）
- 版本分布（在线设备固件版本占比，用于判断覆盖度）
- 单台设备升级次数（防升级风暴/循环升级）

## 七、回答规范

- 不能只写"支持 OTA"，必须给出**灰度比例 + 熔断阈值 + 回滚机制 + 签名校验**四项
- 低功耗/窄带设备必须提示电量、信号、流量成本
- 涉及量产设备时提示"出厂固件需支持 OTA 自举"（老固件不支持升级会导致后期无法远程修复）
