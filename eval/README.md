# 评测集使用说明

这不是一份「提问清单」，而是一套**可执行、可复现、可判分**的验收工具：给定专家的一次真实回答，脚本自动判定它达标还是空泛。

上一轮审核的结论是「沙箱评测未达标准 / 低质量」。问题不在于专家会不会说，而在于**没有客观证据证明它说得到位**。这套评测集就是那份证据。

---

## 一、目录结构

```
eval/
├── cases.json        28 个用例：提问、必备项、禁用项、章节要求、人工评审要点、权重
├── run_eval.py       评测运行器：自动判分 + 生成报告（零第三方依赖）
├── prompts/          用例卡：每条用例一张，照着发、照着存
├── answers/          答案存放处：<用例ID>.md，文件名必须与 ID 一致
└── samples/
    ├── good/         合格样例答案（用于验证判分器不会误杀）
    └── bad/          缺陷样例答案（用于验证判分器能抓出问题）
```

## 二、三步跑完

```bash
# 第 1 步：生成用例卡（已生成过则跳过）
python eval/run_eval.py --init

# 第 2 步：逐条在专家中心发送 prompts/<ID>.md 里的提问，
#        把完整回答原样存成 eval/answers/<ID>.md（只放回答正文，不要放提问）

# 第 3 步：判分
python eval/run_eval.py
```

产物：

- `eval/report.md` —— 人读报告：总评、分类得分、逐用例失分项、红线明细、人工评审勾选清单
- `eval/report.json` —— 机读结果，可接入 CI

只测某几条：

```bash
python eval/run_eval.py --only ACC-01 ACC-02 DQ-01
```

CI 模式（不达标退出码 1）：

```bash
python eval/run_eval.py --strict
```

## 三、判分规则

每个用例基线 100 分，**均摊**到该用例的检查项上：

| 检查项 | 判定方式 |
| --- | --- |
| 章节结构 | 标题行（`#` / 加粗行 / 有序列表）中命中任一近义词即通过，题注优先、正文兜底 |
| 必备关键词 | 每组近义词命中任一即通过（如「字节序 / 字序」） |
| 表格 | 存在合法 Markdown 表格分隔行 |
| 禁用表述 | 命中任一即该检查项失败 |
| 实质长度 | 去空白后的字符数 ≥ 下限 |
| 反问次数 | `？`/`?` 计数 ≤ 上限（仅对显式声明该限制的用例检查） |
| 语种一致 | 英文用例要求中文占比 < 15% |
| 格式红线 | 波浪号与删除线语法：围栏代码块**内**豁免，代码块外一律判违规 |

红线命中额外扣分：每次 5 分，单用例最多扣 20 分。总分按用例权重加权平均。

评级：A ≥ 90，B ≥ 80，C ≥ 70，低于 70 为 D。**建议提交审核的门槛：总分 ≥ 85、红线零违规、覆盖率 100%（28/28）。**

## 四、判分器本身的验证（冒烟基线）

判分器如果只会给高分，评测就没有意义。因此用一对刻意构造的样例做正负对照，结果已固化：

| 样例 | 得分 | 说明 |
| --- | --- | --- |
| `samples/good/ACC-02.md` | **100** | 合格答案，12/12 检查项通过，零红线 |
| `samples/bad/ACC-02.md` | **37** | 5/12 通过；被抓出缺功能码、缺字节序、缺系数、无测点章节、长度不足、含波浪号 |

复现：

```bash
python eval/run_eval.py --answers eval/samples/good --only ACC-02
python eval/run_eval.py --answers eval/samples/bad  --only ACC-02
```

幻觉控制另加一组正负对照（`HAL-01`）：

| 样例 | 得分 | 说明 |
| --- | --- | --- |
| `samples/good/HAL-01.md` | **100** | 对条款号/报价/联系人明确标注【待核实】，给核实渠道与替代方案 |
| `samples/bad/HAL-01.md` | **25** | 编造了精确年费、手机号邮箱、条款号与生效日期，四项必备检查全灭并命中禁用表述 |

另做了 5 项格式负向单测，全部符合预期：

| 输入特征 | 预期 | 实测 |
| --- | --- | --- |
| 出现双波浪号包围的文字 | 检出删除线 | ✅ 检出 |
| 出现全角波浪号（U+FF5E） | 检出 | ✅ 检出 |
| 波浪号位于 ``` 代码块内 | 豁免不误报 | ✅ 未报 |
| 用连接号 `–` 表示区间 | 不误报 | ✅ 未报 |
| 一次回答 3 个反问（上限 2） | 检出 | ✅ 检出 |

## 五、28 个用例覆盖什么

| 分类 | 数量 | 覆盖点 |
| --- | --- | --- |
| 设备接入 | 4 | 传感器批量接入、Modbus RTU 电表、NB-IoT 水表低功耗、MQTT/CoAP/HTTP 选型 |
| 物模型测点 | 3 | 空压机四层建模、测点表 13 字段完整性、简单设备也必须有测点层 |
| 数据质量 | 4 | 四维体检、CSV 文件质检、无文件场景给采集模板、异常率归因进阶方法 |
| 方案成本 | 3 | 智慧工厂上云全案、成本必须声明非正式报价、自建 vs 公有云取舍 |
| 安全与运维 | 3 | 安全接入五层、OTA 灰度与回滚、告警分级与去抖收敛 |
| 边界稳健 | 4 | 「你好」不全流程、信息极少给假设、英文提问全英文、非 IoT 问题划边界 |
| 格式红线 | 2 | 数值区间禁用波浪号、测点表用表格承载 |
| 幻觉控制 | 1 | 诱导编造制度条款/精确报价/联系人，验证拒答与三级可信度标注 |
| 一致性 | 1 | 同条件重复提问，验证协议与阈值结论不漂移 |
| 兜底与纠错 | 1 | 用户纠错 + 防爆区域转人工路径 |
| 响应稳定性 | 1 | 超复杂任务下结论先行与分批交付 |
| 异常处理 | 1 | 工具、知识、权限三重失败下的优雅降级 |

其中 `ACC-01`、`DQ-01`、`SOL-01` 一一对应上架卡片的 3 条快捷提问，是与审核方最先接触的三条，权重最高（各 6）。

**为什么要有边界四例**：上一轮低质量的核心怀疑点就是「开场连环反问」「工具不可用时卡死」。这四例把「首答必须有实质内容」「反问不超过上限」「不暴露内部流程名」变成可判分的硬约束。

## 六、扩展用例

在 `cases.json` 的 `cases` 数组追加一项即可，字段如下（除 `id/title/prompt/weight/category` 外均可选）：

```json
{
  "id": "ACC-05",
  "weight": 4,
  "category": "设备接入",
  "title": "用例标题",
  "prompt": "发给专家的原话",
  "expect_sections": [["章节A", "同义A"], ["章节B"]],
  "must_any": [["同义词1", "同义词2"], ["必含词"]],
  "forbid": ["禁止出现的表述"],
  "must_table": true,
  "min_len": 400,
  "max_questions": 3,
  "lang": "en",
  "rubric": ["人工评审要点一", "人工评审要点二"]
}
```

追加后记得同步 `meta.totalCases`，再跑一次 `--init` 生成新用例卡。

设计原则：`must_any` 每组用**同义数组**而非单一词，避免专家换个说法就被误判；`forbid` 只放确实不该出现的表述，不放风格偏好。
